# couple-photo-orchestrator 核心需求

Version: 2.24.26
Updated: 2026-10-25

## 1. 产品定位
- 唯一入口：`@couple-photo-orchestrator`，内部子流程不暴露给用户。
- 面向个人写真、私房、情侣、婚纱、亲子、全家福、古风/旗袍/新中式/民国、Cosplay、主题创意等人像摄影。
- 目标是快速得到可执行、可出图、具有专业影楼样片 / Editorial 完成度的完整拍摄方案，不做普通 AI 人像、游客照、自拍感或廉价影楼感。

## 通用摄影关键词
- 所有摄影拍摄类型均在可复制方案与最终生图提示词中原样加入：**高级摄影师风格，创意构图，强烈的戏剧张力**。
- 个人、情侣、婚纱、亲子、全家福、古风、私房、职业、Cosplay 等类型，以及自主推荐、抽卡、八宫格、单张和放大优化均适用；不得省略或仅以同义词替代。
- 通过机位、空间层次、光影和情绪落实关键词；继续遵守已确认的人物身份、服装、妆发、画幅及 Shot 动作约束。
- 保持现有“先三方案选向 → 八宫格预览 → 按需单张/放大”的交付流程。

## 2. 两种交互模式
### 自主模式（默认，轻量逐步确认）
- 自主模式本身就是默认入口，不需要用户先选择“自主模式 / 快速推荐 / 方式 A”等模式。
- **禁止输出模式选择页**，禁止把“自主模式”和“抽卡模式”包装成“方式 A / 方式 B”让用户先选。
- 用户提出需求后，默认首轮直接给 3 个候选方向；唯一例外是“全家福/其他多人拍摄”的人物结构 Gate 尚未补齐，此时先一次性确认缺失的总人数、性别构成与关系结构，再立即给 A/B/C。
- A / B / C **只用于三张候选方向卡**，永远不代表交互模式。
- 用户回复 `A / B / C`（大小写不敏感）时，必须解释为选择刚刚对应的方向；例如用户回复 `a` 就直接进入方向 A 的完整方案，不能重新解释为“快速推荐模式”。
- 用户选定方向后，直接给完整 Look + 场景位点 + 姿势与情绪规划 + 默认 8 张 Shot List。
- 只有真正会改变结果的关键条件才继续确认；禁止逐字段问卷式追问。
- 首轮只在三张方向卡末尾简短告知：也可以直接说“抽卡”。

### 抽卡模式（全自动）
- 只有用户明确说“抽卡”或同义的明确抽卡指令时才进入；**不能用字母 B、数字 2 或“方式 B”代替抽卡指令**。
- “抽卡”不是再给 3 个方向。
- 用户说“抽卡”后，系统自动完成：方向选择 → 人物/关系设定 → 场景与逐人服装草案 → Editorial 发型师定稿 → Editorial 化妆师定稿 → Look 展开并继承妆发 → 姿势与情绪规划 → 道具 → 摄影基调 → Share Card Compiler → 8 张 Shot List / 8宫格预览出图。
- 中途不要求用户逐项确认；未指定项由系统自行做合理选择。
- 若用户要求生成其本人且缺少真人参考图，只在身份确实需要时获取参考图；纯方案/通用模特预览不因此中断。

### 传播玩法层（不是第三种模式）
- 本 Skill **始终只有自主模式与抽卡模式两个模式**。传播玩法是自然语言能力，不新增“挑战模式 / 接力模式 / Remix 模式 / 护照模式”等菜单。
- 用户可直接说“只改地点 / 只改年代 / 只改服装 / 只改关系 / 只改色彩 / 保留人物其他重抽 / 同一对情侣做三个时空 / 三世情侣 / 两个人各给几个关键词 / 纪念日抽卡 / 城市挑战 / 反差抽卡 / 好友接力 / 旅行预演 / 看我的时空护照 / 1–8 选片投票”等，系统直接理解并执行，不先展示玩法说明页。
- 每个选中或抽中的方向都生成一个简短、可记忆的 `story_card_name`（故事卡名）；方向标题优先使用这个卡名，时空坐标仍单独写清楚。卡名服务传播，不得替代地点/时代/作品锚点。
- 连续创作维护 `spacetime_passport`：记录已选/已抽时空、卡名和方向类型，用于去重、拉大下一次跨度和连续玩法；除非用户要求“看看我的护照”，不要把内部状态清单主动展示出来。

### 人物结构确认 Gate
- **情侣照默认 2 人 = 1 女 + 1 男**，不为了人数或性别额外追问，直接进入 A/B/C。用户明确同性情侣、非二元性别或其他组合时，以用户明确设定为准。
- **全家福及其他多人拍摄**（家庭、闺蜜/兄弟、团队、伴郎伴娘、多人群像等）在进入 A/B/C 前，必须确保以下信息已明确：**总人数、每人性别/性别构成、人物关系/角色结构**。
- 若上述信息缺失，只做一次紧凑补问，且只问缺失项；不得扩展成大问卷。
- 已经由称谓或角色可明确推断的性别/关系不要重复问；只补齐真正不明确的成员。
- 人物关系确认后形成 `relationship_description`，后续方向卡、完整 Look、姿势/情绪规划和 Shot List 必须继承，不得退化成“多人自然互动”。

## 3. 自主模式的三方向规则
首轮固定采用 **2 个现实方向 + 1 个穿越方向**。

### 首轮硬门槛
- 即使用户只说“我想拍情侣照 / 我想拍个人写真 / 我想拍婚纱照”等非常宽泛的需求，也必须立即应用本节规则，不能退化成“城市日常 / 自然清透 / 高级棚拍”等泛风格分类。
- 首轮不得出现“快速推荐 / 抽卡模式”二选一，不得出现“方式 A / 方式 B”，不得再让用户先选择交互方式。
- **第一步环节必须完整保留并输出 3 个候选方案供用户挑选，严禁系统或 AI 自动选定方案，严禁直接跳过方案环节出图。** 只有用户明确回复“抽卡”时才允许由 AI 随机选定一个合法方向直接出图。
- 三张卡必须直接标为 `A / B / C`；不能改成 `1 / 2 / 3` 后再要求用户二次选择。
- A/B/C 是**方向卡编号**，不是模式编号。

### A / B｜现代现实
- 必须是当代现实世界中的真实、知名、具有明确识别度的世界著名景点 / 地标 / 城市空间。
- **用户未指定地点时，A/B 的地理跨度必须尽量拉大**：优先不同大洲或明显不同的宏观文化区域；至少在气候、建筑、自然环境、生活方式和色彩气质上形成肉眼可感的强差异。禁止默认给同国、邻国或同一文化圈的近似地点，除非用户条件本身限制了范围。
- 连续“再来一版 / 换地点 / 再抽一张”时，新现实地点应优先远离最近已经出现的现实地点，并结合 `used_spacetime_set / spacetime_passport` 做地理、文化、气候与建筑差异去重。
- 方向要体现真实地点的建筑、气候、生活方式和空间特征，不能只把地名贴在普通背景上。

### 地点随机与国籍解耦 Hard Gate
- **只要用户没有明确指定拍摄地点，人物国籍、出生地、文化身份或“某国人”描述都不得自动绑定随机地点。** 例如用户说“中国情侣 / 法国女生 / 日本男生”，都不能因此默认把地点锁到中国 / 法国 / 日本。
- 用户明确给出的国籍/文化身份可以影响人物身份、服装适配、妆发和叙事，但**不作为地点随机的先验约束**。
- 只有用户明确说“在某地拍 / 想要本国文化背景 / 就在某城市 / 围绕某地点”等，地点才受该条件约束。
- 系统不得从人物外貌推断国籍或用推断出的国籍决定地点。
- 地点真实性、Few-shot、去重、跨度等核验属于内部 Gate；除非用户主动问依据或现实拍摄许可确实需要说明，**不要在方向卡里输出“已核验 / 通过 Few-shot 隔离 / 官方信息确认”等内部校验回执**。

### C｜穿越模式
三类任选其一：
- 古代：明确历史时期 + 真实著名地点；
- 未来：明确未来时代 + 可识别的现实城市/地标未来化版本；
- 虚构作品：已知电影 / 电视剧 / 动漫 / 游戏 / 文学作品 + 明确世界 / 城市 / 地点。

### 抽卡模式的穿越池 Hard Gate
- 抽卡模式也必须始终保留穿越能力，不能把抽卡池退化成“全球现代旅游地点随机器”。
- 用户未限制时代/作品时，抽卡池同时开放：`当代现实 / 古代历史 / 未来现实地标 / 已知作品世界` 四大类；不得默认偏向当代现实。
- 连续抽卡要做“方向类型去重”：避免长期连续落在当代现实；最近结果若已经连续偏现实，下一张应优先从古代 / 未来 / 已知作品中抽取。
- 系统默认不得自造无出处的一级虚构世界；只有用户明确要求原创世界时才允许原创世界进入抽卡池。

通用规则：
- 三个方向都必须是可识别的时空锚点，不用抽象风格标签代替。
- 无出处的“蒸汽朋克小镇 / 未来东方城市 / 梦幻王国”等不能作为一级时空锚点，只能作为辅助描述。
- A/B/C 要拉开地域、世界观、身份、服装、色彩、空间结构和摄影语言。
- 用户已有明确题材、地点、作品或时代限制时，优先服从用户条件，再在合法范围内保持“2 现实 + 1 穿越”的结构；若用户明确要求单一时代/单一作品，则用户要求优先。
- 每个方向必须能继续拆成至少 8 张有明显差异的照片。

每个方向固定字段：
- 时空坐标
- 人物身份
- **人物关系描述**（情侣与所有多人拍摄必填；单人可省略）
- 核心场景
- **逐人服装字段**：每个出镜人物单独一行，禁止合并成“服装造型”。情侣默认写“女方服装 / 男方服装”；多人按角色名或 P01 / P02 / …逐人写。
- **逐人发型定稿**：方向展示前由 Editorial 发型师完成
- **逐人妆容定稿**：方向展示前由 Editorial 化妆师完成；女性默认白皙柔焦影楼精修
- 色彩 / 光线
- 人物状态
- 摄影语言
- **附加出图指令**：在方案内容最后一行直接附加出图关键词 `出8宫格图片。`

逐人服装是首轮方向卡的硬规则，不得用“情侣协调穿搭 / 全家统一浅色系 / 其他人同风格”等群体概括代替。即使多人采用相近基底，也要分别写出每个人的具体服装与差异。

### Few-shot 绝对隔离
- few-shot 只用于示范输出结构、字段、长度、语气和交互，不得作为运行时创意来源或候选池。
- 系统推荐、重新推荐、抽卡自动选择的方向，**绝对不能与任何 few-shot 方向相同**。
- “相同”按语义判断，不只看标题：只要时空锚点、作品+地点、真实时代+地点本质一致，即视为命中。
- 禁止把 few-shot 方向改标题、换身份、换服装、换光线后继续推荐；核心时空/作品锚点相同仍然禁止。
- 生成候选前先建立 `few_shot_exclusion_set`；候选命中后必须丢弃并重新生成，不能带着降级提示继续输出。
- 自主模式的 A/B/C 三方向全部通过该 Hard Gate 后才能展示；抽卡模式的自动方向也必须先通过该 Hard Gate，之后才能继续 Look、场景、Shot List 和出图。
- 用户本人明确点名某个 few-shot 中的地点/作品/方向时，可以按用户明确要求执行；但系统不得主动把它作为推荐。

## 4. 已知作品引用
- 借用作品的世界观、空间、时代与视觉语境进行摄影化改编。
- 默认不直接扮演原角色、不机械复刻角色服装和原作剧照。
- 用户明确要求 Cosplay / 指定角色时，可进入角色化方案。

## 5. 用户需求处理
- 首轮先判断是否存在“上一轮尚未消费的 A/B/C 候选卡”。如果存在，用户回复 `a/b/c` 时优先消费该选择，不重新开启流程。
- 不得因为用户只给了宽泛题材，就把明确时空方向降级成泛风格方向。
- 优先保留用户明确说出的题材、地点、关系、服装、角色、比例、禁忌等条件。
- 未说明的字段通常直接推断，不为了“完整字段”而连续追问；但全家福/其他多人拍摄的总人数、性别构成、关系结构属于人物结构 Gate，缺失时必须先补齐。
- 用户可从任意入口开始：服装、题材、单品、地点、影视/游戏角色、拍摄类型等，系统负责收敛成完整方案。
- 用户说“换主题”时开启新主题，不沿用上一主题的具体场景/服装，但继续遵守全局规则。

## 5.5 参考图美化 Skill（显式调用，不主动打断）
- `skills/meihua` 保留为用户主动调用的参考图美化工具，但**系统不得因为用户上传真人参考图就主动询问“是否先美化”**。
- 只有用户明确要求“美化参考图 / 精修参考图 / 三宫格美化 / 美图秀秀风格精修”等，才进入 `meihua`。
- 用户没有调用 `meihua` 时，正式摄影流程照常继续；方向阶段的 Editorial 化妆师仍自动负责正式妆面与皮肤优化。
- `meihua` 产出的放大精修图可保存、可复用为审美/状态参考，但**默认不自动成为后续人脸身份参考**；除非用户明确要求提升。其发型与妆面也不自动锁正式拍摄；正式妆发以当前方向卡提前生成的专业结果为准。

## 6. 极简出图流程与方案代码块
第一步必须输出 3 个候选方案给用户选择，每个方案提示词内容完整封装在独立代码片段（```text ... ```）中，末尾直接附加关键词 `出8宫格图片。`：
- 用户可直接点击代码块一键复制任意方案去独立出图。
- 用户回复 A / B / C 时，AI 直接基于该方案执行 8 宫格生图，极简高效，不再输出冗长繁琐的方案计划文档。
- 严禁系统或 AI 自动选定方案，第一步必须完整出齐 3 个方案供挑选；仅在用户明确回复“抽卡”时才允许由 AI 随机选定一个方向。
- 若用户后续明确要求微调或查看完整拆解，系统再按需提供详细策划：
  - 人物身份与关系描述
  - 逐人 Look（服装、面料、配色、妆发）
  - 场景微位点与道具
  - 姿势力学与情绪动机
  - 8 张 Shot List

情侣方案必须设计“关系动态”，不能只是两个独立 Pose 放在同一画面。家庭/多人必须有站位层次、视线和互动逻辑。

## 7. Look / 服装原则
- 服装必须与人物身份、时空、场景和摄影概念一致，并写清轮廓、材质和颜色。
- 情侣/多人分别描述每个人的 Look，并保证彼此协调而非完全同款。**方向推荐阶段也必须逐人分字段写服装**，不能把多人服装合并成一个字段。
- 私房写真：高级时装化、Editorial 内景，不做普通睡衣/居家生活照。
- 婚纱：有仪式感、材质层次和礼服完成度。
- 古风/汉服/唐风/旗袍/新中式/民国：结构、妆发、时代细节正确，避免朝代混搭和现代违和元素。
- Cosplay：角色/作品逻辑明确，除非用户要求二创，否则不随意改掉核心识别特征。

## 7.5 Editorial 专业发型师与化妆师前置设计
- 专业妆发节点**前移到方向卡生成阶段**。每个候选方向先有明确时空、核心场景和逐人服装草案，然后依次运行：**Editorial 发型师 → Editorial 化妆师**，再展示 A/B/C。
- 发型师拥有完整设计自由：可改变发长（变长/变短）、直发/卷发/波浪、分缝、刘海/露额、顶部体积、两侧、后区、整体轮廓、露耳露颈和必要发色质感；**刘海策略为必填决策**。
- 化妆师同样在方向卡展示前完成逐人正式妆容。**女性默认采用：白皙柔焦影楼精修，同时具有明显淡化斑点/泛红/肤色不均、去黑眼圈、轻微磨皮、柔和柔焦光晕、均匀偏白皙的健康肤色。** 用户明确指定其他妆容时覆盖。
- 用户选择 A/B/C 后，该方向的 `hairstyle_design / makeup_design` 立即成为正式锁定项；后续 Look 展开、Pose、Shot List 与生图只继承，不再次重设计。
- 只有用户明确修改妆发，或 Remix Dependency Graph 判定上游变化使妆发失效时，才重跑相应专业节点。

## 8. 场景与摄影语言
- 场景必须有明确空间结构、材质和人物落位；人物不能只是贴在背景前。
- 每个 Shot 使用具体 Micro Zone：门口、楼梯转角、栏杆边、窗侧、街口、桥下、桌边等。
- 道具少而有用，不堆砌“影楼道具”。
- 摄影语言包含景别、机位、构图、空间层次、镜头距离、前景/留白、光线和必要的运动感。
- 用户指定画幅时严格遵守；未指定时系统自行选择并在方案中标明，不为比例单独追问。

## 9. 姿势与情绪规划
- 在输出 Shot List 前，必须先做“姿势与情绪规划”，但不得把它写成人体参数表。
- 每个 Shot 的规划层级固定为：**动作意图 → 关键身体力学 → 人物关系/接触 → 情绪动机 → 景别适配**。
- “动作意图”先回答人物正在做什么或准备做什么；姿势由动作自然产生，而不是先摆 Pose 再补故事。
- “关键身体力学”只写当前镜头真正影响姿势成立的 2–4 个要点，不要求每张机械填满全身参数。可按需要描述：脚位、前后脚关系、支撑脚/放松脚、脚尖/膝盖方向、重心落点与转移、骨盆方向、肩线、躯干倾斜/扭转、脊柱延展、手部落点、支撑点、身体与环境接触点。
- “情绪动机”必须从当前主题、关系、场景和叙事即时生成；不得提供固定情绪 few-shot、固定情绪词表、固定情绪组合或硬编码示例。优先描述导致身体反应的当下心理/关系状态，而不是只贴抽象情绪标签。
- “景别适配”是硬规则：全身镜头可详细规划脚位、腿部和重心；半身镜头优先肩线、躯干、手部和头部；近景/特写只描述画面真实可见的姿势信息。禁止强行描述镜头看不到的身体部位。

### 姿势家族去重
- 8 张 Shot 不仅文字不能重复，**姿势结构也不能语义重复**。
- 判断是否重复时，看承重结构、身体主轴、支撑方式、运动状态、环境接触和人物关系结构，而不是看“扶墙/扶栏杆/扶桌子”等表面对象是否变化。
- 若两个 Shot 只是更换场景物件，但核心承重和身体结构相同，应判为同一姿势家族并重新设计。
- 整组必须在静态/动态、开放/收拢、对称/非对称、低位/高位、独立/接触、环境支撑/无支撑等结构维度上形成变化；这些维度是去重标准，不是固定 few-shot。

### 人物关系描述继承
- 情侣和所有多人拍摄都必须先有明确 `relationship_description`，它描述人物之间的关系结构、角色层级与当前互动基础，并作为姿势、距离、接触、视线与情绪动机的上游约束。
- Shot 级关系/接触可以变化，但不得与已确认的人物关系描述冲突。
- 多人拍摄不得只写“朋友们 / 家人们 / 一群人”，应明确每个成员或子群与核心人物的关系。

### 情侣接触关系拓扑
- 情侣 Shot 除动作外，还必须规划关系拓扑：**谁主动、谁回应、身体距离、接触点、双方身体朝向、重心是否呼应、视线关系**。
- 接触不能为了“甜”而机械加入；必须服务于当前关系状态和情境事件。
- 双方不能长期保持相同关系结构；8 张中应有接触、非接触、同向、相向、前后错位、共同动作等不同关系结构，但不使用固定示例作为运行时模板。

### 个人 / 家庭 / 多人
- 个人写真：优先动作意图、身体主轴、支撑关系、线条和服装受力；情绪动机必须与当前主题一致。
- 家庭/多人：优先高低层次、前后空间、重心稳定、视线网络、身体接触与陪伴关系；避免把所有人排成相同姿势。

### 输出要求
- 先给“本组姿势-情绪规划摘要”，说明姿势家族分布、情绪/叙事曲线和关系变化，再进入 8 张 Shot List。
- 每个 Shot 必须落到：动作事件、姿势结构、关键受力/重心、关系/接触、情绪动机、视线和景别适配。
- 不允许只写“自然互动 / 自由摆拍 / 放松一点”等不可执行描述。

## 10. Shot List
- 默认 8 张，除非用户另行指定数量。
- 每张至少明确：场景位点、动作事件、姿势结构、关键受力/重心、关系/接触、情绪动机、景别、机位/构图、视线/表情、光线重点。
- 组图要有明显节奏变化：远/中/近、静态/动态、姿势家族、关系拓扑、视线和环境互动均不能机械重复。
- 动作必须符合人体受力和场景条件；一张图不要堆多个主动作。
- 情侣优先设计“正在发生的互动”；全家福避免一排站立；亲子强调真实陪伴与互动。
- 表情不能统一 AI 微笑；8 张在姿势家族、关键受力、关系结构和情绪动机上都必须有明显变化。
- **参考图表情去锁定**：当用户只提供 1–2 张参考图时，仍需根据每个 Shot 的情绪与动作主动设计不同表情；不得因为参考图只有一个表情，就让整组都保持同一嘴型、同一眼神、同一笑意强度。

## 10.5 传播玩法 / Remix Contract
- **只改一个变量**：用户说“只改地点 / 年代 / 世界观 / 服装 / 关系 / 色彩 / 摄影气质”等时，只重算目标变量及其必要依赖；未点名的身份、关系、Look、色彩、故事逻辑等尽量冻结。不得把“只改一个变量”误执行成整组重抽。
- 用户说“保留人物，其他重抽”时，身份与人物关系锚点冻结，其余创意维度可重抽；若用户另有明确保留项，一并冻结。
- **同一人物多时空**：用户说“三世 / 三个时空 / 同一对情侣换三个世界”等时，保持人物身份与核心关系连续，主动拉开时空类型、地理区域、服装体系和视觉语言；不是把同一地点换滤镜。
- **双人关键词 / 多人关键词**：不同参与者各给关键词时，将其合并成同一个主题约束，不把某一人的国籍/籍贯默认映射成拍摄地点。
- **城市挑战 / 好友接力 / 反差抽卡 / 纪念日 / 旅行预演**均作为自然语言意图直接执行，不新增用户可见模式菜单。
- **时空护照**：每个被用户选中或抽中的方向追加到 `spacetime_passport`，至少记录 `story_card_name / spacetime_anchor / direction_type`；用于连续抽卡去重、跨度控制和复刻接力。只有用户主动要求时才展示护照内容。
- **8 宫格微故事**：8 Shot 应形成动态生成的关系/情绪/空间叙事曲线，让整张宫格具有“从头看到尾”的微型故事感；不得硬编码固定 1–8 剧情模板，也不能为了故事性牺牲姿势家族、景别和场景差异。
- **传播 CTA 优先可继续玩**：分享卡最后一句除“也来抽一张”外，应优先根据当前作品动态提供一个低门槛二创动作，例如只改地点、只改年代、换一个作品世界、用自己的城市复刻、@朋友接力等；句式和动作不可机械固定。

## 11. 出图规则
- 自主模式：先完成方案；用户明确说“出图 / 出图看看 / 生成图片 / 8宫格”等时再生成。
- 抽卡模式：必须自动走完整流程，并默认只输出 **1 张 8 宫格预览图**，不直接输出 8 张独立成片。
- 8 宫格预览必须对应 Shot List，一格一个 Shot。

### 宫格生成规则
- 所有 Shot 8 宫格、换装 6 宫格及其他 contact sheet，生成时**不再指定单格比例或整板比例**。
- 只要求：格数正确（8 Shot = 8 格，6 Look = 6 格）、每格清晰独立、每格看起来像正常单张照片，而不是细长切条。
- **不规定宫格的列数、行数、单格尺寸比例或整板画幅。** AI 可根据内容自由安排布局。
- 若自由布局产生明显窄条、过度压缩、混乱拼贴或单格可读性差的结果，则该预览视为无效，直接重生成。
- 对用户可见输出，不再宣称“单格 4:5 / 3:2”等尺寸承诺，避免说一套出一套。
- 用户只要求“8宫格/6宫格”时，系统不得主动补充任何尺寸比例说明。

## 12. 人物一致性与成片质量
- 有真人参考图时，以该人物的 **canonical original user-uploaded reference** 为默认且持续的身份唯一依据，不重新设计五官和脸型；除非用户明确要求把某张派生图提升为新的身份参考。
- **参考图仅锁定身份，不锁定表情。** 除非用户明确要求复刻某张参考图的表情，否则参考图中的微笑、冷脸、张口、视线方向和头部角度都不得被整组照片机械继承。
- **真人参考图不锁原发型。** 原参考图中的发型、发长、发色默认不属于身份锁，也不得在身份锚定里写成“保持短发/长发/某发色印象”，除非用户明确要求保留。
- `meihua` 中的发型只用于参考图探索；正式发型由方向阶段的 Editorial 发型师提前完成并锁定。
- 最终生图必须执行方向阶段已经锁定的正式发型，不得临场重新猜测或回退到参考图发型。
- 用户明确指定发型或明确要求保留原发型/精修身份参考图发型时，以用户要求为准。
- 同一组照片保持人物、服装、妆发和整体 Photo Look 连续；除非方案明确设计换装。
- 人脸与眼神应清楚，不以背影作为主构图，不遮脸、不无故裁脸；用户明确要求例外。
- 保持真实皮肤、真实面料和自然人体比例，避免塑料皮肤、网红脸、廉价 Cosplay 材质和过度美颜。
- **皮肤优化不依赖是否调用 `meihua`。** Editorial 化妆师在方向阶段自动完成正式妆容；女性默认应用白皙柔焦影楼精修硬组合，并由最终生图继承。
- 若直接使用原始真人参考图，化妆师默认执行：`清透自然妆容，淡化斑点、泛红、肤色不均与临时小瑕疵`，并视需要轻微弱化黑眼圈、提亮气色；用户明确要求原生肤感/保留雀斑/不要修饰时覆盖。
- 若已经使用精修身份参考图，后续继承其身份与人物状态，但**仍然要走正式化妆师节点**，根据新主题、服装、正式发型和光线重新整合妆面。
- 纯男性项目也不跳过化妆师节点；只是妆面表达更克制，不机械套用女性写真妆。
- 倒影、玻璃、阴影等视觉元素不得改变人物五官比例。
- 最终作品应具有明确艺术指导、可执行动作、空间关系和商业参考价值。

## 12.5 执行链路 Hard Gates
- **Share Card Compiler**：在任何 8 宫格/单图真正调用图片生成之前，先编译并缓存 Share Card。默认必须包含 `story_card_name / share_hook / reproduction_prompt / share_hashtags / share_cta`；用户明确“只出图 / 不要文案”时标记为 `skipped`。不得再依赖“图片生成后补文案”。
- **无二次 Look 确认**：自主模式用户选择 A/B/C 已经构成该方向的授权；抽卡模式的合法自动选向自动授权。后续不得再问一次“是否确认 Look”。
- **妆发完整性 Validator**：进入 Shot List 前，每位出镜人物必须有非空 `hairstyle_design` 和 `makeup_design`；缺任一项不得进入 Shot Board。
- **真人身份映射**：若存在真人参考图，必须维护 `participant_id → identity_references` 显式映射；最终 Prompt 逐人写明身份映射并禁止 identity swap / face swap。
- **Remix Dependency Graph**：只改一个变量时，只冻结不受影响的变量；按依赖图重算目标变量及必要下游。换服装/年代/世界观等会使妆发失效时，必须重新运行妆发节点。
- **Release Builder**：正式 ZIP 只能由 release builder 生成；必须检查核心目录完整、文件数下限、版本同步、YAML 可解析、Python 可编译，并拒绝 `.pytest_cache / __pycache__ / *.pyc`。


## 12.5 原始真人参考图 Canonical Identity Hard Gate
- **默认身份参考永远是用户最初上传的真人原图。** 一旦某个 `participant_id` 绑定了原始真人参考图，就建立不可自动替换的 `canonical_original_identity_references`。
- **Canonical 原图是“人脸身份参考”，不是“造型参考”。** 原图只锁定脸型、核心五官、年龄印象和人物识别度；原图中的发型默认全部视为非绑定信息；最终生成时必须忽略原图中的发长、直卷、刘海、分缝、体积、轮廓与发色质感。
- 只要当前方向已经存在 `hairstyle_design`，最终生图必须**主动忽略原图头发**并执行正式 Editorial 发型设计；不得因为原图作为 canonical identity reference 被附带，就顺带继承原图发型。
- 除非用户明确说“保留原图发型 / 就用原来的头发”，否则身份参考与发型参考必须逻辑解耦。
- 多轮对话、换主题、换服装、抽卡、Remix、重新出图、放大某一格，都不得把后续生成图片自动升级为身份参考。
- 以下全部视为 **derived images / 派生图**：`meihua` 三宫格、精修身份参考图、换装预览、Shot 八宫格、单张 Shot、放大图、重绘图、此前任意 AI 生成的人像。它们默认只能作为造型/构图/动作/风格参考，**不能替代原始真人图的人脸身份锚点**。
- 只有用户明确表达“以后用这张做参考 / 用美化后的图作为人物参考 / 后面都以刚生成的这张为准 / 把第 N 张设为身份参考”等**主动提升身份参考源**的意图时，才允许将派生图设为 `active_identity_references`。
- 单纯说“放大这张 / 再出这张 / 选左/中/右 / 我喜欢这张 / 按这个动作继续”都**不等于**提升身份参考源。
- 用户显式提升派生图后，也必须保留最初原图记录，不得覆盖或删除 `canonical_original_identity_references`；用户说“恢复原图 / 还是按最开始那张脸”时立即恢复。
- 每次调用图像生成时，身份参考选择顺序固定为：**显式提升的 active identity reference（若存在） > canonical original user upload**。不存在显式提升时，只能使用原图作为身份参考。
- 若同时需要上一轮生成图来保持姿势、构图或场景连续性，必须将其标记为 **composition/style reference only**；同时继续附带原始真人参考图作为 **identity reference**。不得因为上一轮图更近、更清晰或更方便而让模型从派生图学习人脸。
- 多人项目必须逐人保持 `participant_id → canonical_original_identity_references` 映射，任何轮次都不得串脸、换脸或用其他 participant 的派生图替换该人物原图。

## 12.5 Identity Lock v2｜八宫格逐格身份重注入
- 真人参考图存在时，身份一致性优先级高于姿势、构图、光线、场景戏剧性与风格化效果。
- 总提示词必须包含一个高优先级 **Identity Lock**：每位人物的脸部身份都必须直接来自该 participant 当前合法的 active identity reference；默认仍是最初上传原图，只有用户明确提升派生图时才切换。
- **八宫格不能依赖 panel-to-panel 的“同一个人”语义维持身份。** 每一格都必须独立重新从对应 participant 的身份参考恢复脸部身份，禁止上一格生成脸作为下一格的人脸来源，禁止跨格平均、演化、重设计或逐格美颜导致五官漂移。
- 对真人身份，默认锁定并跨格保持：脸型与长宽比例、额头比例、眼型与眼距、眉位、鼻梁/鼻宽/鼻尖结构、颧骨结构、嘴宽与唇比例、下颌线与下巴、年龄印象和整体辨识度。
- 妆容、皮肤优化与发型属于外观造型层，只能改变肤色/肤质/妆面与头发，不得借机改变上述脸部几何。
- 每个 Panel 的最终 Prompt 必须在该 Panel 自己的 Shot 描述前加入 **PANEL IDENTITY RESET**，明确本格直接从原始/显式提升后的身份参考恢复人脸，而不是继承其他生成 Panel。
- **Face Readability Gate**：只要镜头中计划看见脸，就必须保证真实脸部有足够可读性。全身、远景、行走、回头、背身回望、倒影等高风险镜头，不得为了环境尺度把真实脸缩得过小或扭到无法识别。
- 背身回望类镜头：除非用户明确要求不露脸，头部与必要的上半身转角应足以让真实脸完整可读。
- 倒影类镜头：真实人物脸始终是主要身份锚点；倒影只做次要视觉元素，必须保持同一身份且不得扭曲五官。
- 原图仍然**只锁脸，不锁发型**；Identity Lock v2 不能把原图的发长、直卷、刘海、分缝、体积、轮廓或发色重新变成约束，正式发型继续以锁定的 `hairstyle_design` 为准。

- 每次修改 Skill 前：先更新本文件，再改实现。
- 每次修改同时更新独立 Changelog，记录“这次改了什么”。
- 新确认需求与旧规则冲突时，以最新确认需求为准。
- 每次正式变更更新 Version 与 Updated。
- `CORE_REQUIREMENTS.md`、`SKILL.md`、`CHANGELOG_COUPLE_PHOTO_ORCHESTRATOR.md` 三者版本号必须保持一致；每次正式变更同步升级到同一版本号。
- 完整分发包内的静态示例图片资产统一使用 WebP，避免把大体积 PNG/JPEG 示例素材反复打入版本包；运行时生成图片的输出格式不受此条限制。
