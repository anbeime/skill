# 技术方案 Deck · 逐页 Speaker Notes（GOAI 赛道一 · Agent Infra 新智基座）

> 篇幅分配遵循赛道一评审权重：场景价值 25% + 多 Agent 协同 25% + Skill 体系 25% + 工程落地 20% + 开源 5%
> 初赛以方案设计为主，不强制可运行代码；本 deck 含可运行证据（验收脚本 PASS）作为加分。
> 选题方向：**方向三 · 软件研发全流程协同**（缺陷/需求聚合 → 代码根因定位 → 修复生成执行 → 测试发布确认 → 复盘沉淀）。

## P1 · 封面
- **标题**：Antinet·八官署：多 AI 知识库中间层（软件研发全流程协同）
- **副标题**：GOAI 赛道一 · Agent Infra 新智基座 · 方向三「软件研发全流程协同」选型
- **一句话定位**：把「明朝内阁」治理体系映射为多智能体协作框架，文档/缺陷/需求进、四色卡片出、知识回流回库。以**开发者**为最终用户，系统成为**多 AI 协作的知识库中间层**——让研发闭环的每一步都可审计、可复现、可降级。本方案是「知识库中间层」平台在方向三的旗舰实例化。

## P2 · 方法纠偏：从付费刚需反向定义产品
- **起点纠偏**：不从「我的技术能套哪些场景」出发，而从「用户现在就付费 / 低效忍受的真实刚需」反向定义产品，再用四色卡片系统去套。
- **验证三问**：每个场景必须具备 ① 明确付费方 ② 可被八署闭环解决 ③ 四色卡片天然适配——三者缺一不立项。
- **由此得出选型**：选「软件研发全流程协同」为旗舰场景（开发者是付费方代表），并进一步演化为「多 AI 知识库中间层」平台，而非一个单点 Demo。
- **演讲要点**：评委看的是「真实需求 × 可复用能力」，不是技术堆砌；方法纠偏决定了我们交付 Production 而非 Demo。

## P3 · 场景与痛点（场景价值 25%）
- **选题实例化**：围绕「缺陷/需求聚合 → 代码根因定位 → 修复方案生成与执行 → 测试验证与灰度发布确认 → 上线复盘与研发知识沉淀」构建多 Agent 闭环。
- **用户与系统角色**：最终用户是**开发者**；八官署系统定位为**多 AI 之间的知识库中间层**——不同 Agent（或人类工程师）围绕同一份结构化知识（四色卡片 + 知识图谱）协同，而非各自维护私有上下文。
- **真实痛点**：研发团队在 Issue/日志/用户反馈中识别矛盾根因、产出可验证的修复方案；传统单 Agent 把聚合/定位/修复/验证搅在一起，难审计、难降级、难复现，复盘知识随人走、不回流。
- **行业普遍性**：信息过载、结论难溯源、知识难沉淀，同样存在于金融风控、客服复盘、运维复盘；本方案能力可跨场景复用（四付费场景共享同一底座，见 P18）。
- **演讲要点**：我们选具普遍性的企业级问题，且明确系统作为多 AI 知识中间层，而非堆一个 Demo。

## P4 · 核心解决方案总览
- 八官署：指挥使/锦衣卫/密卷房/通政司/监察院/丞相府/军机处/太史阁——**通用底座**，四场景共享。
- 四色卡片（蓝事实/绿解释/黄风险/红行动）作为全链路结构化上下文介质——也是**多 AI 共享的知识中间层载体**。
- 太史阁先做知识回流（读库再干活）、后做沉淀（产出回库）；下方以方向三研发协同为例展示闭环映射，其他场景同理复用。
- **研发闭环映射**：需求/缺陷聚合→通政司蓝卡；根因定位→监察院绿卡；修复方案+执行→丞相府红卡+军机处；测试/发布确认→锦衣卫+军机处；复盘沉淀→太史阁回流。
- **演讲要点**：职责隔离 + 上下文不互相污染，是多智能体走向 Production 的关键；系统作为知识中间层让多个 AI 围绕同一份事实协同。

## P5 · 八官署架构与 Agent Identity（多 Agent 协同 25%）
- 8 个不同职能 Agent，逐一给出身份属性/能力边界/协同关系（详见《Agent Identity 清单》附录 A）。
- 指挥使=主控，锦衣卫=唯一出域审批方，密卷房=解析，通政司=蓝卡，监察院=绿卡，丞相府=红卡，军机处=核验，太史阁=记忆。
- **演讲要点**：每个 Agent 职责清晰、可独立验证、可独立降级。

## P6 · 以 AgentTeams 为协同设计基点
- 角色编排 ↔ 八署具名角色；任务拆解 ↔ 指挥使状态机；上下文传递 ↔ 四色卡片 cite 链；协同执行 ↔ 八署 pipeline；状态追踪 ↔ 太史阁+provenance。
- 迁移到 AgentTeams 运行时只需协议适配，不需重设计工具调用链（见《八官署→AgentTeams 映射》文档）。
- **演讲要点**：不是「提一下工具名」，而是五大能力逐维映射。

## P7 · 主链路时序与闭环（软件研发全流程协同）
- 缺陷/需求流入（Issue+日志+用户反馈）→ 指挥使拆解 → 锦衣卫安检（敏感/越权不过则中止）→ 密卷房解析（代码/日志/Issue 结构化）→ 通政司蓝卡（聚合去重后的事实：复现步骤/报错/影响面）→ 监察院绿卡（根因定位：因果链+影响面分析）→ 丞相府红卡（修复方案：owner+due+验收标准）→ 军机处执行与核验（自动化编码/PR）→ 测试验证与灰度发布确认（锦衣卫+军机处）→ 太史阁回流（复盘沉淀入研发知识库）→ 指挥使聚合返回开发者。
- **闭环关键节点**：任务前检索历史沉淀（先读库再干活，复用过往根因/修复）、任务后回流产出（知识复利，下次同类缺陷秒级定位）；高风险动作（如出域发布、自动合并）由指挥使状态机触发**审批 / 回滚 / 审计**。
- **演讲要点**：完整覆盖方向三「缺陷/需求聚合 → 根因定位 → 修复生成执行 → 测试发布确认 → 复盘沉淀」五段闭环，并满足规则要求的「输入→拆解→上下文→工具→验证→证据→审批回滚→经验沉淀」八步。

## P8 · 四色卡片数据模型（Skill/协同的交付物）
- 蓝卡：可验证事实（quote+paper_id+location+parser）
- 绿卡：因果/Gap（必 cite 蓝卡，gap_type 三选一）
- 黄卡：合规/风险（risk_level+触发规则）
- 红卡：可执行下一步（owner+due+accept_criteria，必 cite 绿/蓝卡）
- **演讲要点**：结构化交付物天然满足「每条结论点回原文」，契合可检查信号；也是多 AI 之间唯一共享的上下文介质。

## P9 · Skill 工程体系（Skill 体系 25%）
- Skill 是必选项：本方案 15 个真实可运行 Skill，核心 8 个给出完整规格（名称/用途/输入与输出/调用条件/依赖工具/失败处理机制/安全边界/复用价值/与多 Agent 协同流程的关系——共 9 项，见《Skill 工程体系》）。
- 示例：`four_color_cards`（四色卡片）、`knowledge_graph`（图谱）、`infographic`、`html_report`、`report_automation`、`ppt_structure_draft`、`card_filter`、`chart_recommendation`。
- **演讲要点**：Skill 是能力抽象层而非一次性行为；可热插拔、可多场景复用、可独立部署。

## P10 · Skill 与多 Agent 协同关系（软件研发闭环）
- 图示（研发场景）：指挥使→`card_filter`/任务拆解；锦衣卫→密钥扫描/OA黑名单/出域审批；密卷房→代码解析/日志结构化/格式转换；通政司→四色卡片（缺陷/需求聚合）；监察院→根因定位/`knowledge_graph`；丞相府→修复方案/PR草稿；军机处→自动化编码执行/报告自动化；太史阁→研发知识库回流/图谱视图。
- **新增强化 Skill（研发向）**：`defect_aggregator`（多源缺陷/需求去重）、`root_cause_locator`（代码根因+影响面）、`fix_generator`（修复方案+编码执行）、`test_release_verifier`（测试/灰度发布确认）。
- **演讲要点**：每个官署的能力由 Skill 承载，工具调用链清晰、可替换；系统作为知识中间层，多个 AI 围绕四色卡片协同而非各自为政。

## P11 · 等价集成契约（MCP-free 等效方案）
- 本方案未使用 MCP，但提供**等价外部工具集成契约**，满足规则「如不使用 MCP，应给出等价集成契约（协议/鉴权/Schema/错误/审计/迁移成本）」要求。
- **契约共性**：每个外部工具抽象为可被 Skill 稳定调用的能力，具备 名称 / 调用入口 / 参数 Schema / 返回结构 / 权限范围 / 失败重试 / 幂等控制 / 审计日志 / 降级方式。
- **工具 1 · 代码仓库 API（缺陷/PR 同步）**：HTTPS/REST(JSON) + Token；输入 repo/issue_id；输出 diff/status；超时/限流 → 回退本地规则库并标注置信度；请求与结果入 provenance；迁移 MCP 成本 低（包一层 MCP Server 暴露同 Schema）。
- **工具 2 · 本地 NPU 推理（Genie qwen2.5vl3b:8910）**：HTTP/OpenAI 兼容，本地无鉴权；输入 prompt+context；输出 completion；模型不可达 → 关键词降级（标注 llm_involved=false）；不记录原文；迁移 MCP 成本 低。
- **工具 3 · 本地规则库（军机处降级）**：进程内 Python 调用；输出 规则结论+置信度；规则缺失 → 返回未知；入 provenance；迁移 MCP 成本 中（需封装为独立工具服务）。
- **结论**：后续迁移到 MCP 只需协议适配（包一层 MCP Server），不需重新设计工具调用链。

## P12 · 可观测与 RAG（满足 2/4 项要求）
- 从「Agent 记忆存储、知识库 RAG、共享状态管理、轨迹可观测」四项中已实现 **3 项**：
  - 太史阁 = 记忆存储 + 共享状态管理（向量检索 + 知识回流）
  - provenance 日志 = 轨迹可观测（Trace/Log/Metrics，可回放）
- RAG 作为推荐项未强制使用（已以记忆+共享状态+可观测三项超额满足「至少 2/4」）。
- **演讲要点**：我们没有堆工具，而是说明必要性与权限边界。

## P13 · 异常分支与降级（多 Agent 协同 25%）
- 指挥使异常熔断：任一官署失败 → 规则引擎降级而非整系统崩溃。
- 大模型掉线：四色卡片回退关键词分类（如实标注 `llm_involved=false`）。
- 解析失败：密卷房三级 fallback（PyMuPDF→pdfplumber→MinerU）。
- 工具核验不可达：军机处回退本地规则库并标注置信度。
- **演讲要点**：降级是设计一等公民，不是补丁。

## P14 · 安全边界与审批回滚（工程落地 20%）
- 锦衣卫：Sci-Hub 等侵权源硬编码拦截；`no_local_cache_as_production=true` 防假全文冒充；密钥扫描（对应场景1「企业AI编码合规审计」的 secrets 出域防控）。
- 数据不出域：默认本地 NPU 推理，无网环境可用。
- 高风险动作：审批/回滚机制由指挥使状态机管理（复赛接入 Higress 网关治理）。
- **演讲要点**：合规与安全是系统底座，对应新智基座「可观测审计」精神，也是四付费场景中「编码审计」场景的刚需。

## P15 · 工程落地与可复现（工程落地 20%）
- `python scripts/run_survey.py` 主链路端到端跑通（八署 pipeline 可复现），已验证可在研发场景复用（缺陷聚合→根因→修复→验证）。
- `python scripts/verify_production.py` 输出标准化 JSON，`consistency:PASS`，退出码 0，可接入 CI；幂等可重跑。
- 已接入真实本地 NPU 模型（Genie, qwen2.5vl3b），`llm_in_loop.used=true`，用于日志/Issue 语义解析与根因推断。

## P18 · 产品化：4 个真实刚需付费场景（场景价值 25%）
- **场景1 · 企业AI编码合规审计**（付费方：企业安全/研发管理）：等保/数据出境硬要求，怕 secrets 出域、AI 擅改生产配置、改完无法追责。套法：黄卡=出域/敏感风险（锦衣卫唯一审批），蓝卡=改动事实+溯源，绿卡=改动因果链，红卡=待整改。产品：私有化「AI 编码审计网关」，按席位/年收费，对标 Snyk/Arnica 专治 AI 代理。
- **场景2 · 跨工具创意生产管线**（付费方：视频/设计工作室、MCN）：文案AI→分镜→Remotion→剪辑→字幕→多平台，6 软件各存各的，版本/素材/决策全散，返工极贵。套法：蓝卡=素材与成片元数据，绿卡=修改理由，红卡=待定稿/审核，黄卡=版权合规。产品：创意生产协同中台，按项目/席位 SaaS，对接 Remotion/剪映/飞书。
- **场景3 · 智能客服知识自演化**（付费方：客服/支持团队，最看好）：传统 KB 建好即 stale，新政策/bug 无人同步，人工维护贵。套法：会话确认新事实→蓝卡，人工纠错因果→绿卡，待补政策→红卡，合规敏感→黄卡；让 KB 从静态文档变带溯源自演化活体。产品：知识库自动化运维 Agent，按对话量/坐席订阅。
- **场景4 · 个性化学习教育陪练**（付费方：教育机构/家长）：现有 AI 辅导无记忆，错点反复错，老师无轨迹。套法：蓝卡=掌握事实/错点，绿卡=错因，红卡=下次该练，黄卡=学习风险。产品：AI 学习档案 SDK，按学生数订阅嵌入网课平台。
- **演讲要点**：四个场景均有明确付费方与四色卡片套法，证明「知识库中间层」不是为单一 Demo 定制，而是跨行业可复用平台。

## P19 · 三步抽象：从场景到平台
- **抽象A · 开放记忆单元**：把四色卡片抽成「带溯源类型的记忆单元」开放格式（不绑 db/UI），4 场景直接接入——地基也是壁垒。
- **抽象B · 通用编排运行时**：把八官署抽成「意图→安检→抽取→审查→策略→执行」通用编排运行时，场景方只写官署插件。
- **抽象C · 分场景发行版**：按场景出 4 个发行版（audit/creative/support/edu），共用底层、分头收费。
- **演讲要点**：场景是入口，平台是护城河；八署与四色卡片从第一天就按「可被 4 场景复用」设计，而非为单一 Demo 定制。

## P20 · 商业模式与核心壁垒
- **商业模式**：底层中间件开源获客 + 行业发行版收费 + 企业私有化高客单。
- **核心壁垒**：「溯源 + 类型 + 跨进程同步」组合——向量库只管存、Agent 框架只管跑、KB 只管文档，无人把「可审计记忆总线」做成标准件，属真实空白地带。
- **风险自知（已消解）**：① 做开放协议而非中心化产品；② 先跑通自家地基（D-2 链接污染 / D-3 wiki 回流 / D-7 db 分裂，均已于 2026-08-06 完成）再对外讲底层——当前已具备对外讲述地基的资格。
- **演讲要点**：我们不卖一个 Agent，我们卖「多 AI 之间可审计的记忆与编排标准件」。

- 数据集 OpenAlex（CC0）合法复用。
- **Skill 生态开源（对题要点）**：核心 Skill 抽象层与 `github.com/anbeime/skill`（公开技能商店，跨框架技能包，支持 claude/hermes/openclaw 等）接口对齐；迁移到新运行时只需按 `SKILL.md` 协议适配，**无需重写业务逻辑**——把 P6 的「迁移只需协议适配」落到真实开源资产上，证明可替换性非口头声明。研发向 Skill（根因定位/修复生成/测试确认）亦遵循同一契约，可上架该商店被外部 Agent 复用。

## P22 · 可替换性论证：自研八署 vs 推荐工具链
- 赛道推荐工具链（AgentTeams 必选 + Nacos/Higress/PolarDB/RocketMQ/LoongSuite 推荐）。本方案以自研八署实现，论证逐组件可替换性（接口兼容、替换原因、迁移成本）：
  - **AgentTeams**：已逐维映射（见 P6/映射文档），迁移成本 低。
  - **Nacos（配置/服务发现）** → 本地 YAML + AgentRegistry 等价；迁移成本 低。
  - **Higress（网关/鉴权/路由）** → 指挥使状态机 + 锦衣卫审批等价；复赛接入成本 中。
  - **PolarDB（向量/长记忆/RAG/审计）** → 太史阁本地向量库 + provenance 等价；迁移成本 低（换存储后端）。
  - **RocketMQ（事件驱动/Agent 间消息）** → 八署 pipeline 串联等价；迁移成本 中。
  - **LoongSuite / AgentScope Studio / AgentLoop（可观测）** → provenance 日志等价；迁移成本 中（接入 Trace 后端）。
- **论证结论**：全部推荐组件均可在不重设计工具调用链前提下替换，接口兼容；评审重点（设计理念/接口契约/必要性/可替换性/权限边界/闭环证据/迁移成本）逐条覆盖。

## P23 · 差异化亮点 vs 单 Agent / 通用框架
- 可审计：太史阁全链路留痕 + 监察院合规检查，研发闭环谁/何时/对哪个缺陷产出根因都可回放。
- 结构化：四色卡片比纯文本报告/单 Agent 对话可检查，且作为**多 AI 知识中间层**被共享。
- 降级与容错：指挥使熔断 + 锦衣卫扫描，大模型挂掉/解析失败不崩盘。
- 复用：15+ Skill（含研发向根因/修复/测试）可脱离八署独立部署，亦可挂接公开技能商店；四付费场景共用同一底座。
